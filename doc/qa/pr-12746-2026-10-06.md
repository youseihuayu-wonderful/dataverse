## 1. Actual multipart roundtrip

A deterministic **20,971,520-byte (20 MiB)** binary file was uploaded through the real SPA file input at `localhost:8000/modern` using the existing `s3` driver.

The supported JVM setting `dataverse.files.s3.min-part-size=8388608` was supplied through an external QA-only override. The source default is 1 GiB; the default threshold was not exercised, and no upload code was changed.

Observed browser traffic:

- Three signed S3 part PUT requests, with `partNumber` values 1, 2 and 3 and multipart upload IDs: all **HTTP 200**.
- Browser CORS preflights succeeded; each part exposed a readable `ETag`.
- Dataverse multipart completion PUT: **HTTP 200**.
- The actual **Save Changes** action registered the file and its 20 MiB metadata.
- The actual **Original File Format** menu action performed the Dataverse access request and followed **HTTP 303** to S3 **HTTP 200**.
- The completed browser download had the original byte count and SHA-256:

```text
3568217a72eed5450d704907de96e14c75cc1b18661f38e0c9f458e462b38def
```

### Additional frontend limitation observed

A separate custom S3 driver named `multipartqa` also uploaded, completed, saved and downloaded correctly through the backend API. Its SPA download menu was hidden.

[`AccessFileMenu.tsx`, lines 56–60](https://github.com/IQSS/dataverse-frontend/blob/1e586a09691f880376939ddf924bf1bdba94c307/src/sections/file/file-action-buttons/access-file-menu/AccessFileMenu.tsx#L56-L60) checks whether `storageIdentifier` starts with `s3`, rather than identifying all configured S3 driver IDs. The complete SPA roundtrip above therefore used the original `s3` driver. No frontend workaround or source fix was applied. This is an observed frontend limitation, not an established new defect caused by this backend PR.
